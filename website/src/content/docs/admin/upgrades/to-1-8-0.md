Your data, keys and settings carry over; update the tag as described in [Tags and updating](/admin/upgrades/). Take a [backup](/admin/backups/) first: 1.8.0 changes the database, and the backup is one of the two ways back.

## Going back to 1.7.x

Going back to 1.7.x is only possible with the downgrade migrations from the 1.8.0 image (`alembic downgrade 20261118a2`) or by restoring the backup taken before the upgrade; 1.7.x does not start on a database migrated by 1.8.0.

Run the downgrade with the 1.8.0 image while the hub is stopped, then start the 1.7.x image. Jobs stored by 1.8.0 stay readable for 1.7.x after the downgrade.

## Job error texts

The `error` of a failed job (`GET /api/v1/jobs`) now carries a fixed text per error code, for example `print_failed: The label could not be printed.`. The error message of the printer, which can name its address, goes to the server log only. Structured values (the expected and loaded tape width, the labels the printer confirmed) stay in the job's error detail.

The first start of 1.8.0 rewrites, once, the `error` of jobs that failed before the upgrade with a free text after their code: the code stays, the text becomes the fixed text of that code. Errors that are already a fixed text, a bare marker such as `printer_interrupted`, a class name, an error that names its cause code (`outcome_unknown: tape_empty`) and errors with a code the hub does not know are kept as they are. The free text is gone after that; the downgrade does not bring it back.

## Connection test of an integration

The connection test (**Settings → Integrations → Test connection**) reads at most 64 KiB of the answer, asks for an uncompressed answer and refuses a compressed one (`probe_compressed_body`), and ends within the integration's timeout as a whole, not per read. Only the status of the answer counts, as before.

## Lookups of a batch have one deadline

The integration lookups of one batch print, sheet print or render check now share one deadline, the setting `integrations.lookup_batch_deadline_s` (environment `LABELYARD_LOOKUP_BATCH_DEADLINE_S`, default 30 seconds, at most 300). Waiting for the shared lookup bound counts towards it. An item not looked up by then fails with `lookup-timeout`: a batch or sheet print answers `504`, a render check gives that item the verdict `lookup-timeout`. An integration error before the deadline keeps its own code (`integration_lookup_failed` and the others). A single lookup keeps its own limit.

## Previews of signed-in users and the number of render slots

The hub draws at most `render.max_concurrent` pages at once (sheet previews, calibration pages, page jobs): environment `LABELYARD_RENDER_MAX_CONCURRENT`, settings API or settings import, `2` to `16`, default `2` as before. A change applies once no render holds a slot.

Each signed-in browser session is now its own owner, like an API key, and all of them count together with the page jobs and other callers without a key as one group. That group never holds the last slot, so API keys can always render. What this means:

- **With the default 2 slots all signed-in users share one slot.** While one user's render is stuck, that session gets `429` (`too-many-previews`) and every other signed-in user `503` (`render-unavailable`) until the render ends.
- **From 3 slots signed-in users render side by side**: a stuck render of one session no longer refuses the others while a slot of the group is left.

Callers with neither a key nor a session (Pangolin SSO without a hub session) are part of the same group.

## Request headers are bounded

The image now starts uvicorn with the h11 HTTP parser (`--http h11`) instead of httptools, and sets `--h11-max-incomplete-event-size 16384`. The h11 parser is the main change. The 16 KiB bound applies to request data that stays incomplete across several reads; a complete header block that arrives in one read is not limited by this flag. This applies to every deployment, with or without a proxy. A reverse proxy in front stays recommended: it terminates TLS, sets its own limits and keeps slow clients away from the hub.

If you run the hub with your own `command:` or `uvicorn` call, add `--http h11 --h11-max-incomplete-event-size 16384` to keep the same bound.

## A printer that could not be wired is shown

When the hub cannot wire a printer (an unknown model, a printer that does not answer, saved settings that are not valid), the printer read now says so. `GET /api/v1/printers`, `GET /api/v1/printers/{id}` and the admin printer routes gain three fields: `wiring` (`wired`, `not_wired` or `disabled`), `wiring_reason` (`model_unknown`, `discovery_failed`, `invalid_config` or `unexpected`, else `null`) and `wiring_at` (when the last attempt failed, else `null`). They are additive: nothing is removed or renamed. The reason is a fixed code, never the error text of the printer.

The printer list and the printer page show a printer that is not wired as "Not wired" with the reason in words. The state is kept in memory only: a restart tries the wiring again, and saving the printer under Settings > Printers tries it at once. Nothing changes in the database.

## Public web address of an integration

Snipe-IT, Grocy and Spoolman each get a new setting, the public web address (`integrations.<name>.web_url`, environment `LABELYARD_SNIPEIT_WEB_URL`, `LABELYARD_GROCY_WEB_URL`, `LABELYARD_SPOOLMAN_WEB_URL`; a value set there locks the field). It is the address people open and scan, for example `https://inventory.example.com`, while the base address stays the one the hub uses to reach the app. Only http and https addresses are accepted, without a user name or password, without a query or fragment, up to 2048 characters.

- **The "Open in …" link is gone until you set it.** The `url` of a lookup (`GET /api/v1/lookup/{app}/{id}`) is `null` while no web address is set; with one it is the item's page under that address. The same holds for the `url` of a Grocy battery or chore (`GET /api/v1/lookup/grocy/batteries/{id}`, `…/chores/{id}`).
- **Printed codes follow the web address once it is set.** A label printed for a looked-up item carries the item's address under the web address. Without the setting nothing printed changes: the code keeps the base address as before.
- **The preview draws what prints.** `POST /api/v1/render/preview` accepts `item: {app, id}`; the hub then looks the item up and draws the code the print carries, and a `data.qr_payload` sent along is ignored. A key with only read scope sees that code only under the web address; while there is none, its preview carries a stand-in code of the same size and the answer the header `X-Labelyard-QR: withheld`. The sheet preview (`POST /api/v1/print/{printer}/sheet/preview`) follows the same rule and marks such a cell with `qr_withheld: true`. Without `item` the preview draws `data` as before.
- **Keys without admin scope no longer see internal addresses.** In every job the hub answers (`GET /api/v1/jobs`, `GET /api/v1/jobs/{id}`, a batch, a retry, a cancel), each `qr_payload` that names an integration's base address is answered in its web form, or `null` while that integration has no web address. The same holds for a printer's queue (`GET /api/v1/printers/{id}/queue`). A code stored under an earlier base address, or for an integration that has been cleared since, is answered as `null`. Admins see the job as stored. Nothing in the database changes.
- **Retrying an old job reprints its stored code.** A retry repeats the stored payload as it is: a tape job printed before the web address was set reprints the base address. Print the item again (not a retry) to get the code under the web address.

## The sheet list is bounded, active sheets are capped, discarded sheets can be purged

- **`GET /api/v1/sheets` answers at most 500 sheets per request.** When more match, the `Link` header names the next page (`Link: </api/v1/sheets?…&limit=500&offset=500>; rel="next"`); the body stays a list of sheets in the same order as before. New query parameters: `limit` (1 to 500, default 500), `offset`, `back_missing` (only sheets whose code on the back is not confirmed yet) and `hide_used_up` (leave out active sheets without a free cell; the answer then carries `X-Used-Up-Hidden` with how many it left out). Every filter is applied before the page is cut. A script that reads the list should follow `Link`; with fewer than 500 sheets nothing changes.
- **Active sheets are capped.** The settings `sheets.max_active` (active sheets per hub, default 1000) and `sheets.max_active_per_type` (per sheet type, default 200), each from 1 to 10000, set through the settings API (`PUT /api/v1/settings`) or a settings import. A new sheet over a cap is refused with `409 sheet_limit_reached` and `error_detail: {cap, scope}` (`scope` is `hub` or `type`), from every way a sheet is created: **New sheet**, a sheet with its code in a cell or on the back, and a sheet print that would open a new sheet (nothing is reserved then). Only active sheets count: discarding a sheet frees room. A hub that already holds more active sheets than a cap when it is updated keeps them, but refuses every new sheet until enough sheets are discarded or `sheets.max_active` / `sheets.max_active_per_type` is raised.
- **Discarded sheets can be purged.** `POST /api/v1/sheets/purge` (admin) with `{"older_than_days": 365}` lists the sheets discarded more than that many days ago, oldest first; with `"dry_run": false` it deletes them with their cells. At most `limit` sheets per call (1 to 1000, default 1000); `more: true` says to call again. On the sheets page an admin finds this as **Purge discarded sheets**. A purged code is never issued again. Jobs that printed onto a purged sheet keep their record; the job page says the sheet was purged, and a retry answers `409 sheet_purged`.

## Three tightenings of what the hub accepts (a `fix`, not a new capability)

- **User info in a stored link is refused.** A source address of a sheet type (`source_url`, also in an import document) and a public web address of an integration must not carry a user name or password (`https://user:secret@host/…`): the hub answers `422`. A link with user info that is already stored stays as it is, but the web app no longer shows it as a link, and an exported type that carries one is refused when it is imported again (`invalid_import`, `type.source_url`). To fix it, open the type under **Sheet archive**, choose **Edit details** and replace the source address by one without user name and password; in an export file, remove the user info from `source_url` before importing. A host label that mixes Latin, Cyrillic or Greek letters (a look-alike of a known name, after IDNA decoding) is refused the same way; names in one script, such as `bücher.example`, are fine. The web app shows the host (punycode form for an international name) next to every stored link.
- **Invisible characters are removed from free text.** The text of sheet types, sheets, cells and designs (names, notes, descriptions, purposes) loses the zero-width space (U+200B), the word joiner (U+2060), the byte order mark (U+FEFF) and the tag characters (U+E0000 to U+E007F) when it is written; U+2028 and U+2029 become a line break (a space in a one-line field); the result is normalised to NFC. The zero-width joiner (U+200D, it holds emoji together) and the soft hyphen stay. A required field that is empty after that is refused as `must not be empty`. Text already stored is not changed.
- **A corner radius is at most half the shorter label side.** A sheet type or version with a larger `corner_radius` is refused with `422 corner_radius_too_large` (the `error_detail` names the field `corner_radius`). A type stored with a larger radius keeps working: the page and the preview draw it with exactly that half.

Importing a sheet type in the mode **Add as new version** onto a verified type now sets the type back to **unverified**: nobody has checked the imported numbers against paper.

## The sheet-type list can be paged, and the archive reads its vendors from facets

- **`GET /api/v1/sheet-types` takes `limit` (1 to 200) and `offset`.** Without `limit` the answer is the whole list as before; with it the `Link` header names the next page. **`GET /api/v1/sheet-types/facets`** counts vendors and page sizes under the list's filters except the vendor.
- **Some sheet type keys are reserved.** A key equal to a fixed path segment under `/api/v1/sheet-types/` (`facets`, `import` and `delete-unused`) is refused with `422 type_key_reserved`, when a type is created and when one is imported (also as a new key). A type that already has such a key is not changed: only its detail (`GET /api/v1/sheet-types/facets`, in the API and in the web app) is unreachable, because that path now answers the facets; export, archive, edit and delete still work (`GET /api/v1/sheet-types/import` is not shadowed, only the static `POST /import` is). To rename it, export it, import the export document under a new key (import mode `as_new_key`) and delete the old type.

## Sheet types come from a catalog

- **A fresh installation starts with no sheet types.** The hub no longer inserts its bundled types on start. You add the types you use from the catalog in the sheet archive. Until one is installed, the calibration page and the page-printer field of the Grocy label settings link to it.
- **An upgraded installation keeps its types.** The first start of 1.8.0 runs, once, the fixes of 1.7.x that an installation has not applied yet (a hub that skipped 1.7.x gets the corrected Avery Zweckform L4731REV and takes over your own type of the key 6121, 3490 or L4737REV, if you had one, as shipped). Then it links every bundled type to its catalog entry. Sheets and custom or imported types do not change. If this step fails, the notification centre says so, and the hub tries again on the next start.
- **Catalog updates are offered, never applied by themselves.** A bundled type you did not edit is offered a newer catalog version as an update. A type you edited (a description, a product code, a QR switch or a new geometry version of your own) only shows that the catalog has a newer version. This includes 6121, 3490 or L4737REV when 1.7.x took over your own type of that key: they keep your fields and show the newer version without an update button.
- **Types and backing designs an older hub missed come from the catalog.** An installation from before 1.7.0 that never received a later bundled type or the UltraGrip backing design does not get it on upgrade: install it from the catalog.
- **The catalog API.** `GET /api/v1/sheet-catalog` (read) lists the entries with `installed`, `update_available` and `catalog_newer`, filterable by `q` (key, vendor, product code), `page`, `vendor`, `w`/`h` and `verified`, paged with `limit` (1 to 200) and `offset`, with vendor and page-size facets; `GET /api/v1/sheet-catalog/{key}` adds the geometry. `POST /api/v1/sheet-catalog/{key}/install` (admin) installs an entry: under its own key as a bundled type linked to the catalog, with `as_new_key` as an imported type without that link. A taken key answers `409 type_exists`, a taken prefix `409 prefix_taken` with a free one in `error_detail.suggested_prefix`. Both ways keep the entry's `verified`. When the entry's backing design differs from your design of the same key, the install or update brings your design to the catalog's only if it is still as shipped; otherwise it answers `409 backing_design_differs` with the design in `error_detail.design`. Other types that use the same design (Avery Zweckform 6121 and 3490 share the UltraGrip design) are updated with it in the same step and listed in `also_updated`, provided each is a bundled type you did not edit and its own catalog entry has the same new design; otherwise the step answers `409 backing_design_shared` with those types in `error_detail.types`, and nothing changes. `POST /api/v1/sheet-types/{key}/catalog-update` (admin) applies an offered update (`409 locally_edited` for an edited type, `409 no_update` when there is none); it adds a geometry version only when the geometry changed, and existing sheets stay on their version.
- **Any type without sheets can be deleted (a loosening).** `DELETE /api/v1/sheet-types/{key}` no longer refuses bundled and imported types; it still refuses a type with sheets (`409 type_in_use`, reason `has_sheets`, archive it instead) and now also a type a Grocy label setting names (reason `type_in_settings`, the setting in `error_detail.setting`). `POST /api/v1/sheet-types/delete-unused` (admin) deletes up to 500 types at once, all or none; a type that has sheets by then answers `409 not_unused`. Backing designs and the sheet code counter of a deleted type stay, so a type added again with the same prefix continues its numbering; jobs and calibrations keep their records. `delete-unused` is a reserved type key from now on.
- **Usage of a type.** Each type in `GET /api/v1/sheet-types` carries `sheets_with_free_cells`, `free_labels`, `sheets_total`, `last_used_at` and `usage_state` (`in_use`, `used_before`, `unused`), plus `catalog_key`, `catalog_revision`, `update_available`, `catalog_newer` and `catalog_missing`. `sheets_in_use` keeps its meaning (sheets of any state). The list sorts by `sort=key|usage|last_used` and filters by `usage_state` and `unused_since` (a date); the facets take `usage_state`.
- **Going back:** the downgrade removes the catalog link of every type, the types themselves stay.

## The sheet code keeps off preprinted areas; the feed mark comes after it

- **The sheet code is placed before the feed mark.** Until 1.7.x the feed mark took the top band's right end first and the margin sheet code chose with what was left. From 1.8.0 the sheet code is placed first and the feed mark takes the right end of the top band if that is free, else its left end, else it is not printed on this page and stays due for the next one. Without preprinted areas the band and the QR of the sheet code stay as in 1.7.x for every type of the catalog (checked for hardware margins of 3 to 6.5 mm). On a narrow sheet or a printer with a small top margin, the sheet code now keeps its QR and the feed mark moves to another page; the margin check (`GET /api/v1/sheets/margin-check`) reports this with `feed_mark_reason: "no_free_place"`.
- **Preprinted areas and the position of the sheet code (new).** A sheet type carries up to 16 rectangles on the front of the sheet where nothing is printed (`preprint_zones`, in mm from the page's top left, each with a note of at most 120 characters) and can link a preprint preset (`preprint_preset`; presets live under `/api/v1/preprint-presets`, admin writes, `409 preset_in_use` while a type links one). `id_margin_band` (`auto`, `top`, `bottom`, `left`, `right`), `id_margin_align` (`start`, `end`) and `id_margin_offset_mm` place the margin sheet code. A named band is a rule: without room there the page carries no margin code. Writes are checked against the current geometry: `422 preprint_zone_off_page`, `422 preprint_zone_overlaps_cell`, `422 id_position_off_page` and `422 id_position_overlaps_cell`. Every existing type keeps `auto` and no zones, which places the code as before.
- **Where the code fits, per printer.** `GET /api/v1/sheet-types/{key}/id-placement` (read) lists, for every enabled page printer the credentials may use, whether the margin code fits, its band, offset and size, and why not (`outside_printable`, `overlaps_preprint`, `too_small`, `no_margin_band`). The margin check and the print preview carry the chosen rectangle (`rect`, `margin_id_rect`).
- **A new geometry version must keep the preprinted areas and the code position valid.** Adding a version (also an import in mode `new_version`) that puts a label cell under a preprinted area of the type or its preset, or makes its configured code position invalid, is refused with `422 preprint_zone_overlaps_cell` or `422 id_position_off_page` / `id_position_overlaps_cell`; adjust the areas or the position first. The hub never drops them by itself.
- **Export documents.** A type with a code position, zones or a preset exports as `format_version: 3`; other types stay version 1 or 2, and older documents import as before. A 1.7.x hub refuses a version-3 document.
- **Going back:** the downgrade removes the presets, the zones and the code position; stored jobs keep the rectangle they were printed with, which 1.7.x ignores. 1.7.x draws a stored or retried page by its band rule again: the sheet code at the start of its band. On a page where the code went to the right end of the top band and the feed mark to its left end, 1.7.x draws both at the left and they overlap; print such a page again on 1.8.0 or skip its retry after the downgrade.

## Calibration prints are numbered

- **Every calibration page and check print is a run with a number per printer and tray.** The numbers start at 1 for every tray, also for trays you calibrated before: pages printed before 1.8.0 have no number. A number is never given out twice; a print whose submit failed leaves a gap. A retry of the job belongs to the same run and keeps its number. The date on the page follows the hub's time zone (`general.time_zone`), also in the PDF download; until 1.7.x it came from the server's clock. The hub keeps the newest 1000 runs per printer and tray.
- **The tray the printer really used.** After a calibration page was printed, the hub asks the IPP printer once which tray it took (`media-col-actual`). When the answer names another tray than the one you chose, the run records it; when the printer does not say, the run shows "not reported". This is one more request to the printer per calibration page and nothing to set up.
- **The run list.** `GET /api/v1/printers/{id}/calibration/{tray}/runs` (read, and access to the printer) lists the runs and the retries of their jobs, newest first, with `run_no`, `kind`, `submitted`, `requested_tray`, `actual_media_source` and `media_source_reported`. A calibration page job carries `run_no`, `time` and `run_id` in its payload's `detail`.
- **Stored calibrations become history.** The first start of 1.8.0 records each stored calibration as the first history entry of its tray (`imported`). The stored values themselves do not change.
- **Going back:** the downgrade removes the runs, their counters, the history and the check sheets; the stored calibrations stay, and 1.7.x prints with them as before. Calibration page jobs keep their run number in the payload, which 1.7.x ignores.

## Every saved calibration is kept

- **A save no longer overwrites the last one.** Every save, reset and restore of a tray's calibration is an entry in its history, written in the same step as the calibration itself. The calibrations you saved before 1.8.0 are its first entries (`imported`). The hub keeps the newest 500 entries per printer and tray.
- **Saved readings decide the values.** `PUT /api/v1/printers/{id}/calibration/{tray}` takes `readings` (3 to 200), `run_id` (the calibration page they were taken on; a run of another printer or tray answers `422 run_not_for_this_tray`, a run printed for another version than `measured_on` `422 run_version_mismatch`) and `note` (at most 500 characters). With `readings` the hub fits them again on the `measured_on` version (now needed with readings) and stores its own fit. A sent value further than 0.05 mm from that fit (scale and rotation: at the page corner farthest from the centre) is replaced; the answer says so with `notes: ["client_values_ignored"]` and names the values in `ignored_fields`. Values sent without readings are stored as sent, as before.
- **The history API.** `GET /api/v1/printers/{id}/calibration/{tray}/history` (read, and access to the printer) lists the entries newest first, 50 per page (`limit` up to 100, `offset`, a `Link` header to the next page), each with its values, the values before it, what changed, the sheet type version it was measured on, its run, readings and note, and `jobs_count` (every key's jobs on the printer; the jobs list shows a key without the admin scope only its own). `POST …/history/{entry}/restore` (admin) uses an entry's values again as a new `revert` entry and never deletes one; an entry measured on a sheet type version deleted since is restored without it (`notes: ["measured_on_deleted"]`).
- **Which jobs used an entry.** A page job printed with a calibration names its history entry in its payload (`calibration_history_id`); `GET /api/v1/jobs?calibration={entry}` lists those jobs. Jobs from before 1.8.0 have no such key; they count for an entry when their calibration values are the entry's and they were created before the tray's next entry.
- **Versions of a sheet type.** `GET /api/v1/sheet-types/{key}/versions` (read) lists the versions newest first, each with the geometry fields changed against the version before it (`changed_fields`, old and new in mm), who added it, when and its note. `POST /api/v1/sheet-types/{key}/versions/{n}/restore` (admin) adds a new version with version n's geometry and the note "Restored from version n"; it is refused with `409 newer_version_in_use` while a sheet uses a newer version.
- **Going back:** the downgrade removes the history (see above); the newest calibration of every tray stays and 1.7.x prints with it. Job payloads keep `calibration_history_id`, which 1.7.x ignores; the calibration values in the payload keep the shape 1.7.x reads. After a downgrade and a new upgrade to 1.8.0 the history starts again from the stored calibrations with new entries, so jobs printed before the downgrade name an entry that no longer exists and count for no entry.

## The calibration page stays inside the printable area and carries its run codes

- **Everything is laid out inside the printer's printable area.** That is the page less the printer's hardware margin of each side (5 mm when the printer does not report it), the tray's stored offset on that axis and 1 mm, the same room the sheet code of a label sheet gets; a check print also keeps clear of where its correction's scale and rotation move the page edges. A corner mark, ruler tick or `S`/`Z` label that would fall outside it is left out as a whole; a cut line is shortened. Until 1.7.x the page kept four empty 15 mm squares at the page corners instead and ignored the printer's margins.
- **Every cell carries its number and an 8 mm cell code** (`LYC1:<run>:<cell>`), centred and clear of the scales and corner marks. A sheet type with QR codes switched off, or a label too small for the code, prints the number only. Corner marks are 0.9 mm long next to a crossing and 1.8 mm at the grid's outer edge (1.5 mm until 1.7.x).
- **Up to four page codes** (10 mm, `LYC1:<run>:0:…` with the sheet type, its version and the correction) sit at the printable corners of the page, or, when the margin is too narrow, in the outer corner of the corner cells; that cell's number then moves to its inner corner. A corner without room has no page code. `GET /api/v1/printers/{id}/calibration/{tray}/page/layout?type=&version=&kind=` (read, and access to the printer) answers how many page codes fit (`page_codes`), the reserved run-line slots, the passes of the sheet and, per block, whether the margin text prints in full, smaller or not at all (`margin_text`, `full` | `reduced` | `omitted`); the run stores where its page codes were drawn.
- **The run information is in two margin blocks.** The top block names the run, its date and time and the kind of page, then the sheet type, version, printer and tray; the bottom block the correction applied (or none), the sheet-type values that differ from the catalog version, and the checkerboard hint where it applies. When the line of sheet type, printer and tray is too long, the printer name gives way first, then the type key, then the tray; the run number, date, time, version and correction values are never shortened. The blocks stay in the margins above and below the grid, never on the labels: where a margin is too shallow at 6 pt the block is printed smaller, down to 4.5 pt, and where even that does not fit it is left out. The page codes carry the run, the sheet type, its version and the correction either way.
- **A downloaded PDF belongs to no run.** It draws the same page as a printed one, with "No run (downloaded PDF)" in place of the run and without codes.
- **A run code too large for its symbol is refused** with `422 calibration_qr_too_large` and is never shortened; the run is taken back and its number stays a gap.
- **Going back:** 1.7.x ignores the new keys of a calibration page job's payload (`prefix`, `allow_qr`, `geometry_diff`, `printable_area`) and draws a retried page with its corner squares again.

## A check print can suggest a sheet geometry

- **The fit names its print.** `POST /api/v1/printers/{id}/calibration/{tray}/fit` takes an optional `run_id`: the print the readings were taken on. A run of another printer or tray answers `422 run_not_for_this_tray`, a run printed for another version than the fitted one `422 run_version_mismatch`. Without `run_id` the fit answers as before.
- **The suggestion.** With the run of a check print whose correction was measured on **another** sheet type, the answer carries `suggestion`: the pitch and margins (in hundredths of a millimetre) that the remaining readings point at, each `null` when it changes by less than 0.05 mm (a smaller change stays when the other value of its axis needs it to keep the grid on the page; both values of an axis are `null` when the geometry rules would refuse it, such as a pitch below the label size on a sheet without gaps, so the suggestion can always be applied), and `uneven` when a reading lies more than 0.3 mm off the straight trend (check the sheet, not the printer). On a calibration page a pitch or margin error looks like printer scale and offset, so there is no suggestion: `suggestion_unavailable` is `no_check_run` for a calibration page or a check print without a correction, `same_type` for a correction measured on this sheet type, and `unknown_correction` when the sheet type the correction was measured on is not known (typed in by hand, or its history entry or version is gone).
- **Apply as a new version.** `POST /api/v1/sheet-types/{key}/versions/from-suggestion` (admin) takes `run_id` and at least one of `pitch_x_mm`, `pitch_y_mm`, `margin_left_mm`, `margin_top_mm` (a margin may be 0), and adds a version with the run's geometry and these values. Its change note names the run by its number. The run must be a check print (`422 run_not_a_check_print`) of this type (`422 run_not_for_this_type`) and of its newest version (`409 run_version_not_current`) that gives a suggestion (`422 suggestion_unavailable`, with the reason of the fit's `suggestion_unavailable`).
- **Going back:** 1.7.x ignores `run_id` in a fit request and has no suggestion; a version added from a suggestion is an ordinary version and stays.

## One check sheet takes up to three passes

- **A check print can reuse its sheet.** `POST /api/v1/printers/{id}/calibration/{tray}/page` takes `check_sheet` (`new` or `next`, only with `corrected: true`). `new` starts a check sheet: pass 1 is the full check page. `next` prints the lowest free pass of the newest open check sheet of that printer, tray and sheet type version; when there is none it answers `409 check_sheet_full`. The pass is taken in the same step as the run number, so two prints never get the same pass; a print whose submit failed frees its pass again. When the run retention drops the run of a printed pass, its sheet is closed, so that pass is never printed twice. Without `check_sheet` a check print is the single full page, as before.
- **What each pass prints.** The passes use crossings that never touch each other, diagonals included: pass 1 the four outer crossings and the centre, the later passes one column and two rows further in, at most three passes. Every pass draws its crosses with the mini scale and a `K1`, `K2` or `K3` label, and no cut lines or rulers. Pass 1 adds the cell numbers, cell codes, page codes (with `:K1`), the corner marks (none around the crossings the later passes use) and the margin blocks; its top line ends with "pass 1 of n". Passes 2 and 3 print nothing else but one run line (`#14 · 2026-11-21 14:05 · K2 · with correction`) in a slot pass 1 left in its margin. Where the margin has no room for the slots, the later passes print their crosses only; the hub still records each pass with its run. A sheet type with fewer than five crossings, or with all of them on one line, takes one pass: the full check page.
- **The open sheet.** `GET /api/v1/printers/{id}/calibration/{tray}/check-sheets/open?type=&version=` (read, and access to the printer) answers the newest check sheet with a free pass (`passes_total`, `passes_used`, `next_pass`, `run_line_slots` and the printed passes with their runs), or `null`. The layout summary (`…/page/layout?kind=check_page`) now counts the passes of the sheet in `passes_total` and the run-line slots for them.
- **The dialog says it first.** Before a check print the web app offers the next pass of the open sheet or a new sheet, and says when the page has room for fewer than four page codes, when it prints without margin text, when it names its run nowhere, and when later passes will print without their run line. The calibration page says the same above its print button.
- **Going back:** the downgrade removes the check sheets with the other calibration tables (see above). 1.7.x ignores the new payload keys `passes_total`, `pass_no` and `pass_crossings`, so a retried pass 2 or 3 prints the full check page on 1.7.x.
